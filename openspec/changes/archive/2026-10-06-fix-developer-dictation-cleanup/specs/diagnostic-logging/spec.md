# Spec Delta

## Purpose

Описывает безопасную локальную диагностику операций Talkee: причину вызова или пропуска обработки, корреляцию этапов и ограниченное хранение файлов для последующего разбора проблем без тел запросов и секретов.

## ADDED Requirements

### Requirement: Correlated processing evidence
Логи SHALL связывать запись, STT, очистку и вставку идентификатором операции и различать новую попытку. Для очистки MUST фиксироваться источник запуска, глобальный/effective-флаг, backend/model/preset, длительность и конечный исход; для отправленного запроса — HTTP-статус либо безопасная категория ошибки и доступные usage/finish_reason. Отсутствующие метрики MUST NOT изображаться нулём.

#### Scenario: Очистка пропущена
- **WHEN** запись не требует очистки или backend не настроен
- **THEN** запись решения содержит request/operation id, флаги и отдельную причину пропуска; ложного сообщения об отправленном HTTP-запросе нет

#### Scenario: Успешный DeepSeek вызов
- **WHEN** пользователь инициирует очистку и провайдер возвращает успех с usage
- **THEN** по одному идентификатору находятся начало, безопасный host/path/model, статус, headers/total duration, usage и применение результата

#### Scenario: HTTP ошибка или таймаут
- **WHEN** запрос получил 401/429/500 либо не завершился в срок
- **THEN** для его начала имеется один конечный исход с категорией ошибки/статусом и длительностью, а диктовка сохраняется через fallback

#### Scenario: Провайдер не вернул usage
- **WHEN** локальная модель или совместимый API вернули content без счётчиков токенов
- **THEN** операция успешна, отсутствие usage явно различимо и не записывается как ноль токенов

### Requirement: Metadata-only local logs
Диагностические логи SHALL оставаться локальными и MUST NOT содержать API-ключи, Authorization, тела запросов/ответов, полные расшифровки или системные промпты. URL MUST исключать userinfo/query/fragment; ошибки MUST записываться безопасными полями. Управляющие символы MUST NOT позволять подделать дополнительные log records.

#### Scenario: Секрет в URL и теле ошибки
- **WHEN** endpoint содержит credentials/query с токеном, а провайдер возвращает тело с текстом запроса
- **THEN** в логе присутствуют только безопасный host/path, статус и категория ошибки, без credentials/query/body

#### Scenario: Расшифровка с переносами
- **WHEN** пользователь диктует многострочную разработческую задачу
- **THEN** лог содержит размеры и этапы, но не содержание задачи; оставшиеся допустимые сообщения не создают поддельных строк логов

### Requirement: Bounded rotating log storage
Логи SHALL храниться в `~/.talkee/talkee.log` и не более трёх архивов `.1`–`.3`. При единственном процессе-писателе каждый файл MUST быть не больше 5 МиБ, суммарно не больше 20 МиБ; старейший архив удаляется. Существующий oversized-файл MUST ограничиваться при первой записи. Ошибка записи/ротации MUST NOT прерывать обработку диктовки.

#### Scenario: Ротация
- **WHEN** очередная запись пересекает границу 5 МиБ
- **THEN** текущий файл становится `.1`, старые архивы сдвигаются, `.3` сверх лимита удаляется, новая запись попадает в active-файл

#### Scenario: Обновление с большим старым логом
- **WHEN** приложение впервые пишет в ранее неограниченный oversized-log
- **THEN** набор файлов приводится к пределу, сохраняет доступный ограниченный хвост диагностических записей и не архивирует весь oversized-файл

#### Scenario: Недоступна папка логов
- **WHEN** запись или ротация невозможна из-за прав/диска
- **THEN** диктовка продолжается без panic и рекурсивного логирования, а безлимитное дописывание не выполняется

### Requirement: Log clearing and inspection
Команда очистки работающего приложения SHALL удалять active и все архивы согласованно с writer; новые записи после очистки MUST формировать свежий ограниченный лог. Новые файлы MUST иметь права доступа только для владельца. Документация и команды просмотра MUST учитывать ротацию и позволять изучать весь сохранённый набор по времени и id операции.

#### Scenario: Очистка архива
- **WHEN** пользователь очищает логи через приложение во время активного writer
- **THEN** старые active/archives удаляются без гонки с ротацией, дальнейшие записи создают свежий лог

#### Scenario: Наблюдение за логом
- **WHEN** запущено `bun run logs` и приложение ротирует файл
- **THEN** просмотр продолжает показывать новые записи active-файла без ручного перезапуска
